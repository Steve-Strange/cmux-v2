# Theming

cmux uses the user's resolved Ghostty theme as the default source for its own
window chrome and for Chrome's toolbar/omnibox colors.

## Source

On macOS and Linux, cmux asks libghostty to load the default Ghostty config
files, finalize the config, then read:

- `background`
- `foreground`
- `palette`
- optional `cursor-color`
- optional `selection-background`
- optional `selection-foreground`

Windows does not link libghostty for theme extraction, so it keeps the built-in
cmux defaults.

Set `"ghostty_theme": false` in `~/.cmux_layout.json` to disable Ghostty-driven
theme defaults.

## Precedence

Ghostty is the default source for themed surfaces and the general accent.
Pane-drop feedback and the pane focus border deliberately default to cmux blue
on every theme. A key literally present in user JSON wins for that slot:

- `~/.cmux_layout.json`: `accent_color` overrides the derived layout accent.
  `drop_highlight_color` and `focus_color` independently customize pane-drop
  feedback and the focused-pane border. Both default to cmux/Bonsplit blue
  (`#007aff`) and are never derived from the Ghostty theme. Set either key to
  another `#rrggbb` value to customize it. The advanced Chrome-surface keys
  `chrome_tab_bar_color`, `chrome_toolbar_color`, `chrome_omnibox_color`,
  `chrome_omnibox_popup_color`, and `chrome_omnibox_popup_hover_color` may each
  be set to `#rrggbb`; an empty or absent key inherits its Ghostty-derived
  default.
- `~/.cmux_rail.json`: every rail color key, including `bg`, `sel_bg`,
  `hover_bg`, `text`, `accent`, and scrollbar/badge/plus colors, overrides the
  derived rail slot.

The rail tweaker writes a full rail JSON file; those written keys therefore
count as explicit overrides.

## Derivation

`cmux_theme.{h,cc}` is the pure, host-tested model. It stores colors as ARGB
`uint32_t`, not `SkColor`.

The derived palette uses WCAG relative luminance to classify the Ghostty
background as light or dark. Light themes darken background tiers; dark themes
lighten them. Window, content, rail, strip, tab, and pane backgrounds are
adjacent but distinct tiers so the layout remains readable.

Text tiers are blended from Ghostty foreground:

| Slot | Source |
| --- | --- |
| Primary text | Ghostty foreground |
| Dim text | Foreground blended over themed background at 70% |
| Folder/plus text | Foreground blended at 84% |
| Faint text | Foreground blended at 45% |
| Accent | `cursor-color`, else ANSI palette index 4, else foreground |
| Hover/selection backgrounds | Low-alpha foreground blended over themed bg |
| Rail drag background | `selection-background` when present, else derived drag bg |

Transient cmux chrome uses the same semantic slots. Pane and tab drag ghosts
use the active-tab background and text. Drop targets use the independent
`drop_highlight_color`, and pane focus borders use the independent
`focus_color`, including when the Ghostty palette defines ANSI blue as another
hue. The sidebar header and resize divider use the rail/pane separator tiers.
These surfaces are wired explicitly because the drag overlay is hosted in a
separate Views widget.

## Chrome Surfaces

cmux does not persist Ghostty colors as a Chrome profile theme or user accent.
Older builds did; on startup cmux migrates an autogenerated theme back to the
default only when its color exactly matches the current legacy cmux surface
seed. User-selected autogenerated colors, extension themes, and other profile
themes are never overwritten.

By default, a final process-wide cmux color mixer maps the sidebar, tab bar,
and outer toolbar to the resolved Ghostty surface. Before those explicit
surface recipes, it replays Chromium's baseline reference and system color
mixers. This prevents a platform or profile accent from tinting menus, bubbles,
security chips, switches, dividers, and toolbar icons while preserving stock
Chrome Material semantics. The omnibox uses Helium's state logic on top of
those Ghostty surfaces: dark mode aliases the popup/results surface, while
light mode uses the active-tab/Surface5-like surface. Hover uses Chromium's
bright-protection state layer over the resolved bar background. Its fixed
geometry is Helium's 28 px control height,
14 px primary type, and 8 px radius.

Focused omnibox borders use Helium primary-40 (`#3551d2`) for light Ghostty
themes and primary-80 (`#bac3ff`) for dark themes. Omnibox text follows the
Ghostty foreground. Text selection uses Ghostty's explicit
`selection-background` / `selection-foreground` when present; otherwise it
uses the mode-appropriate Helium blue with white/black contrast text. Popup
hover/selection uses Chromium's subtle state layer over the Ghostty popup
surface. The five advanced JSON keys above can override those Chrome surfaces
independently.

Chrome Views controls inside the cmux window do not read that profile theme
directly. Normal Chrome browser windows override their `BrowserWidget`
`ColorProviderKey`; cmux uses a plain `views::Widget`, so without an explicit
override the widget falls back to the platform `NativeTheme` (for example,
macOS dark mode), making `kColorToolbar` and the real `LocationBarView` render
dark inside a light Ghostty theme.

On every Ghostty theme apply, startup completion, and `theme.reload`, cmux sets
the top-level widget overrides:

- `SetColorModeOverride(is_light ? kLight : kDark)`
- `SetUserColorOverride(std::nullopt)`

If `"ghostty_theme": false` or extraction fails, both overrides are cleared with
`std::nullopt`, restoring stock `NativeTheme` behavior. Chromium's widget
setters call `ThemeChanged()` when the value changes; `ThemeChanged()` notifies
the view tree and invalidates the widget `ColorProvider`, so toolbar rows,
`LocationBarView`, omnibox children, and other `kColorToolbar` consumers
re-resolve and repaint without restart.

cmux does not change the profile's browser color scheme. Light/dark ownership
is local to the cmux widgets through `SetColorModeOverride`.

### Descendant Widgets

Widget color inheritance was checked against Chromium Views:
`Widget::GetColorProviderKey()` starts from the parent widget's key when
`parent_` is set, then applies the widget's own overrides. Bubble widgets are a
special case: `BubbleWidget::GetColorProvider()` forwards to the anchor's
primary window widget.

Per-widget verdict:

| Widget | Verdict |
| --- | --- |
| Main cmux window | Explicit overrides on apply/startup/reload/clear. |
| Extension action popup (`CmuxExtensionPopupContents`) | Inherits through `BubbleDialogDelegate` anchor; `BubbleWidget` uses the anchor primary widget color provider. |
| Extensions menu (`ExtensionsMenuCoordinator` / `ExtensionsMenuView`) | Inherits through its bubble anchor for the same reason. |
| Tab drag overlay (`cmux-tab-drag-overlay`) | Child popup with `params.parent = host_widget->GetNativeView()`, so its key inherits from the cmux widget. It does not render Chrome-themed controls. |
| Tab, extension action, and toolbar app menus | `MenuRunner` creates `MenuHost` with the invoking widget as owner/parent, so menu widgets inherit the cmux widget key. |
| Undocked DevTools window | Standalone top-level widget, so it does not inherit. cmux registers it for explicit overrides and reapplies them on `theme.reload`; it unregisters on window teardown. |

## Reload

`theme.reload` first re-reads `~/.cmux_layout.json`, including `ghostty_theme`,
`accent_color`, `drop_highlight_color`, `focus_color`, and the five
`chrome_*_color` surface overrides. It then initializes Ghostty's
process-global core on the UI thread before posting the blocking Ghostty config
read to a `ThreadPool` task with `MayBlock`, then applies the result on the UI
thread. It is unbound by default; bind it in the `keybindings` array in
`cmux.json` if desired.

Set `CMUX_THEME_SELFTEST=1` to log a greppable result after apply:

```text
cmux-theme-selftest: PASS source=ghostty is_light=1 bg=#f0f2f6 accent=#4d68b0
cmux-theme-selftest: PASS chrome surface bg=#f8fafd new_tab_bg=#f0f2f6
```

The New Tab canvas uses the resolved Ghostty `background` value exactly. Chrome
surface elevation colors can still be derived from that value, but the page
itself is not replaced by a generic Material light/dark neutral.
